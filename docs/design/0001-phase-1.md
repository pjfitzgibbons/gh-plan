<a id="naming"></a>
## 1. Naming

The tool lives in its own repo, and `.tracker/` lives in whichever repo is being planned
([ADR 0002](../adr/0002-tracker-per-repo.md)).

The tool's repo carries its own Claude Code settings and attribution hook, because that
configuration does not inherit from directories outside the repo. Its own `.tracker/` is the first
plan it tracks.

The repo is `gh-plan`, the product is GH Plan, and the CLI command is `plan`. `gh-plan` is free
on both GitHub and PyPI. Plain `plan` is taken on PyPI, so the package is `gh-plan` and installs
the `plan` command. The `gh-` prefix is what a `gh` extension needs: installed as one, the tool
runs as `gh plan`. It shells out to `gh` only to read pull requests.

<a id="scope"></a>
## 2. Scope

**In:** item schema and validation · cycle detection · SQLite index · `start` / `stop` and the
`post-checkout` hook · `ready.yml` · `next` / `ready` / `why` / `board` / `list` / `show` /
`status` · `new` / `set` / `ice` / `schedule` · `freeze` · `validate` · `reindex` · `sync` ·
`hooks install` · `--json` everywhere.

**Out:** HTML rendering, the web server, drag interaction. Deferred to Phases 2 and 3.

**Acceptance criterion:** Phase 1 ships no HTML and no server, so the terminal has to answer *what
do I do now* well enough to work from. `plan next` (§8.3) is that answer. If it is not good enough
to work from daily, Phase 1 failed and the HTML views of Phase 2 are mandatory.

<a id="phasing"></a>
## 3. Phasing

Each phase is useful on its own.

| Phase | Contents | Standing value if we stop here |
|---|---|---|
| 1: CLI only, terminal views | schema, validation, cycle detection, the start commit and hooks, index, `ready.yml`, `next` / `ready` / `why` / `board`, plus repo setup and tests | Already beats Projects v2: real dependencies, cycle detection, the split rule enforced on write, baselines, evidence in git, no rate limits, and a usable *what-next* answer |
| 2: HTML views | HTML templates, CSS Grid board and timeline, SVG dependency arrows, `plan render` → `.tracker/out/`, then `plan serve` serving the same templates | The board and the dependency arrows |
| 3: write UI | drag to change status and lane | Full replacement |

HTML rendering sits in Phase 2. Phase 1 answers *what next* in the terminal instead (§8.3). Charts
are a presentation upgrade, because every fact a chart would show is already in the index by the
end of Phase 1. The templates and the server land together in Phase 2, since serving an existing
template is nearly free once it exists.

Phase 1 clears more MUSTs than any tool in the survey, including the three that none satisfied.
Phases 2 and 3 are convenience and can be judged later, on evidence.

<a id="layout"></a>
## 4. Layout

```
gh-plan/
  pyproject.toml            # uv, python >=3.14
  src/ghplan/
    __init__.py
    cli.py                  # Typer app — thin; every command delegates to core
    config.py               # config.yml model + discovery
    model.py                # Item, Milestone — pydantic v2
    store.py                # read/write .tracker/ files: YAML, and Markdown with YAML front matter (ruamel.yaml, §6.7)
    ids.py                  # draw a word, resolve what is typed (§6.2)
    blocklist.sha256        # digests of the words a drawn ID never uses (§6.2)
    index.py                # SQLite build + query
    gh.py                   # every subprocess call to gh, in one place
    git.py                  # every subprocess call to git, in one place
    start.py                # plan start / stop: the tool commit, built through git.py (§8.2)
    validate.py             # the rule set, one function per rule
    plan.py                 # duration, schedule, lane heads, next/ready/why
  tests/
    test_validate.py  test_plan.py  test_store.py  test_ids.py  test_start.py
    fixtures/                 # committed .tracker/ trees
```

**Rule: `gh.py` and `git.py` are the only modules that spawn a process.** The `timekeeping/`
adapters of [design 0002](0002-tracked-time.md) are the one other exception. Everything else is pure
and unit-testable against fixtures, which is what makes `plan.py`, the part with the real logic,
testable without a network or a repo.

<a id="discovery"></a>
## 5. Discovery

`.tracker/` is found by walking up from `cwd`, like git: the nearest directory holding `.tracker/config.yml` is the root. `PLAN_ROOT` names that directory and skips the walk. If none is found, exit 2, naming every path searched. A `.tracker/` that holds `config.json` and no `config.yml` is a tracker in the old JSON layout; it also exits 2, naming the converter. Member repo paths in `config.repos` are relative to the root.

<a id="data-model"></a>
## 6. Data model

<a id="item"></a>
### 6.1 Item

```python
# model.py
Estimate = Literal[1, 2, 3, 5]          # 8 and 13 are rejected, not representable
Priority = Literal["P0", "P1", "P2", "P3"]
Status   = Literal["Icebox", "Todo", "In Progress", "Blocked", "Done"]
Type     = Literal["feat", "bug", "chore"]

class Baseline(BaseModel):
    start: date
    finish: date
    frozen_at: datetime
    reason: str

class Item(BaseModel):
    # The ID is the file stem; no field repeats it.
    title: str
    type: Type                           # required; names the branch: feat/, fix/, chore/
    status: Status = "Icebox"
    estimate: Estimate | None = None     # None = needs-triage, or a parent with children
    priority: Priority = "P2"
    ordinal: int | None = None           # writable rank, sparse (100, 200...). Tiebreak in `next`
    lane: str | None = None              # must be in the repo's config.lanes
    milestone: str | None = None         # None <=> Icebox
    labels: list[str] = []
    parent: str | None = None            # an item ID
    blocked_by: list[str] = []           # "<id> - <title>"; the ID part is authoritative
    started: datetime | None = None      # written once, by the start commit
    baseline: Baseline | None = None
```

The fields are declared in the order a file's keys are written (§6.7). An unknown key is an error, so a typo in a hand-edited file fails instead of being dropped. `type` has no default: a file without it fails, and `plan new` writes `feat` unless told otherwise. An item's branch is `<type>/<id>-<slug>`, with `fix` for a `bug`: `feat/`, `fix/` or `chore/`. `parent` and each `blocked_by` entry must start with a well-formed ID. The Markdown body is not a field: `store.py` reads it beside the model and writes it back unchanged.

An item file, `.tracker/items/wa-tunep.md`, in the form every write produces (§6.7):

```markdown
---
title: Retry failed webhook deliveries
type: feat
status: Todo
estimate: 3
priority: P1
ordinal: 100
lane: api
milestone: beta
labels:
  - area:webhooks
parent: wa-ridal
blocked_by:
  - "ba-sokim - Sign webhook payloads"
baseline:
  start: 2026-10-13
  finish: 2026-10-18
  frozen_at: 2026-10-10T16:00:00Z
  reason: Beta checkpoint
---
### Summary
A webhook delivery that fails is dropped. Retry it with backoff before giving up.

### Scope
...
```

The body follows the item outline ([writer conventions §3](../agents/technical-writer.md#technical-writer-issues)): Task, Guardrails, Lenses and Done. `plan new` writes the headings (§8.2). `plan start` writes `started` once ([architecture §7.1](../architecture.md#start)), and `plan freeze` writes `baseline` once ([architecture §7.5](../architecture.md#freeze)). `actual_time`, the tracked-time snapshot, follows `baseline` ([design 0002, *Data model*](0002-tracked-time.md#data-model)).

Absent on purpose: assignee, and the actual finish. The finish is read from the default branch's history (§6.3), so no file holds a date that could disagree with it.

<a id="identity"></a>
### 6.2 Identity

An ID is `<prefix>-<word>`, such as `wa-tunep`, and it is the item file's stem. The prefix is
`config.prefix`, lowercase letters, unique among the repos of any plan that includes the repo. The
word is five letters, alternating consonant and vowel (CVCVC), from 16 consonants and 5 vowels:
16 × 5 × 16 × 5 × 16 = 102,400 words per repo. The consonants are `b d f g h j k l m n p r s t v z`
and the vowels `a e i o u`. `c` and `q` are left out because they sound like `k`, `x` because it is
two sounds, and `w` and `y` because they act as vowels.

`plan new` draws a word at random. A word on the blocklist of words that read badly, or already
used by a file in the repo's `.tracker/items/`, is drawn again. The blocklist ships with the tool as
`src/ghplan/blocklist.sha256`, the same for every repo. It holds each word's SHA-256 digest, one per
line, so the words themselves aren't in the repo; hashing all 102,400 words recovers them in under
a second. There is no counter, so two worktrees creating items at once need nothing merged.

A command that takes an item resolves what was typed in this order, and the first rule that matches
exactly one item wins:

1. a full ID;
2. a word without the prefix, inside its own repo;
3. a unique prefix of a word (`tun`);
4. a unique word from a title;
5. the ID in the current branch's name, `<type>/<id>-<slug>`, when nothing was typed.

Case and surrounding space are ignored, a prefix may carry the repo prefix (`wa-tun`), and a title
word matches a whole word. When no rule matches exactly one item, the first rule that matched
several lists them with their titles, and the command exits 1; nothing matching exits 1 too.
`ids.py` takes the branch name as an argument, and `git.py` reads it. Shell completion offers IDs
with their titles.

<a id="status"></a>
### 6.3 Status

`status` is stored in the item file. The five statuses are fixed, in the order of [`F2`](../requirements.md): `Icebox → Todo → In Progress → Blocked → Done`. They aren't configurable, because `next`, `validate` and the start commit give `Icebox`, `In Progress`, `Blocked` and `Done` fixed meanings that a renamed or missing status would break.

Each status has one way in:

| Status | Set by | Recorded where |
|---|---|---|
| `Icebox` | `plan ice`, which clears the milestone | the item's branch, merged by PR |
| `Todo` | `plan schedule`, or `plan stop` | `schedule` on a branch; `stop` as a tool commit on the default branch |
| `In Progress` | `plan start`, or the `post-checkout` hook | the start, a tool commit on the default branch ([architecture §7.1](../architecture.md#start)) |
| `Blocked` | `plan set --status Blocked` | the item's branch, merged by PR |
| `Done` | `plan set --status Done`, on the item's branch | the squash merge of the item's PR ([architecture §7.3](../architecture.md#finish)) |

`Icebox` must agree with the milestone being absent, and `validate` checks it. `validate` also warns when a stored `Blocked` disagrees with `blocked_by`: no unfinished item blocks it, or an unfinished one blocks an item that isn't `Blocked`.

The actual start ([`C5`](../requirements.md)) is `started`. The actual finish is the committer date of the commit on the default branch's first-parent history that changed the item's `status` to `Done`, read by `git.py` into the index (§7). If that happened more than once, because the item was reopened, the last one counts. Until the item's branch merges, the item is `Done` in that branch's files and has no finish date.

<a id="ordinal"></a>
### 6.4 Ordinal

`ordinal` is a writable integer in the item file, sparse by convention (100, 200, 300…) so an item
can be inserted without renumbering. It is the tiebreak inside a priority band, not a replacement
for priority: an opaque integer carries no intent, while a band plus a tiebreak carries both.

<a id="milestones"></a>
### 6.5 Milestones

One file per milestone, at `.tracker/milestones/<id>.md`, for the same reason there is one file
per item: concurrent edits to different milestones merge cleanly and `git log -p` on one file is
that milestone's history. There is no `milestones_file` key; milestones are discovered by globbing
the directory. The ID is the file stem. The front matter holds `title` and `order` (a sparse
integer; cross-milestone sequence comes from it, not from dependency edges), and the body is the
exit criterion:

```markdown
---
title: Beta
order: 200
---
Every P0 and P1 item in `api` and `frontend` is Done, and signup has run end to end on staging.
```

A milestone named on an item is looked up in the item's own repo first, then in the plan that lists
the repo as a member ([architecture §4.1](../architecture.md#members)). A repo milestone with the
same ID as one in that plan hides the plan's for the repo's items, and `validate` warns.

<a id="config"></a>
### 6.6 Config

`.tracker/config.yml`:

```yaml
prefix: wa
points_per_week: 5.0
project_start: 2026-10-13
hours_per_point: 8.0
repos:
  - ../billing-api
lanes:
  - api
  - frontend
  - docs
  - infra
```

`prefix`, `points_per_week`, `project_start` and `lanes` are required. `repos` lists member repos by path, relative to the root, and is absent in a repo planned on its own; each member has a `.tracker/config.yml` of its own, which names its prefix. `--repo` takes that prefix. `hours_per_point` defaults to the value shown, and it and the optional `time_source` belong to tracked time ([design 0002, *Config*](0002-tracked-time.md#config)). An unknown key is an error, so a misspelt key fails instead of quietly taking its default. A config that can't be read or doesn't validate exits 2, like a missing one.

<a id="file-format"></a>
### 6.7 File format

Every committed tracker file is YAML ([ADR 0007](../adr/0007-tracker-files-are-yaml.md)). Items and milestones are Markdown with YAML front matter, between two `---` lines. `config.yml`, `focus.yml` and `ready.yml` are plain YAML.

A read loads YAML 1.2 with ruamel.yaml's safe loader, `YAML(typ="safe")`, which refuses object tags and duplicate keys. The schema then checks every field's type, and a value of the wrong type fails rather than being converted. A file with no front matter, or front matter that is never closed, fails too. Each failure is a finding that names the file. A read accepts any valid YAML that matches the schema, so a hand-edited file in another layout loads, and the next tool write puts it back in the canonical form. A read also accepts a leading byte-order mark, which some editors add, and the next tool write drops it. A file that is not valid UTF-8 is a finding that names the file.

Every tool write produces one canonical form, whichever command made it:

- The encoding is UTF-8 with no byte-order mark. Non-ASCII text is written as itself (`Café`), never escaped.
- The style is block, with a two-space indent, one key per line and each list element on its own line. Lines are never folded.
- Keys come in a fixed order. An item's are `title`, `type`, `status`, `estimate`, `priority`, `ordinal`, `lane`, `milestone`, `labels`, `parent`, `blocked_by`, `started`, `baseline`, then `actual_time` ([design 0002, *Data model*](0002-tracked-time.md#data-model)). A baseline's are `start`, `finish`, `frozen_at`, `reason`, and an `actual_time`'s are `seconds`, `entries`, `running`, `source`, `key`, `fetched_at`. A milestone's are `title`, `order`. The config's follow §6.6, with `time_source` ([design 0002, *Config*](0002-tracked-time.md#config)) after `hours_per_point`.
- A field whose value is null, or an empty list, is left out. A field equal to its default is still written, so every item file carries `title`, `type`, `status` and `priority`.
- A string that a YAML 1.1 or 1.2 reader would type as something else is quoted: `no`, `yes`, `on`, `null`, `0123`, `1.10`, a date-like string. So is one that YAML could not read plain, such as a title holding `: `. Each `blocked_by` entry is always double-quoted.
- A date is written `2026-10-13`. A datetime is written in UTC to the second, `2026-10-10T16:00:00Z`. A read converts a datetime with another offset to UTC and drops its fraction of a second, and rejects one with no time zone, whose instant is unknown.
- The Markdown body is written back byte for byte, except that a body without a final newline gets one. A plain YAML file ends with a single newline.

Each model declares its fields in this key order, so the writer takes the order from the model and keeps no second list. Comments in front matter and in the YAML files are not kept: a note about a value goes in the body, and the reason for a change in its commit message. `store.py` pins a minimum ruamel.yaml version and uses only the `YAML()` instance API.

The focus file, `.tracker/focus.yml`, names the one fast-tracked feature and exists only while a focus is set. Its keys are `name`, then `parent` (one item ID) or `items` (a list of them), then `reason`, then `set_at`, a datetime. What a focus does to the order of work is #75's design.

<a id="index"></a>
## 7. Index

Rebuilt wholesale, never incrementally. The bound that keeps this acceptable: a full rebuild of 500
items finishes in under one second. Incremental updates are worth building only if a measured
rebuild breaks that bound.

The index is built from the item and milestone files of every repo in the plan, and from each
repo's local git history. `git.py` lists the first-parent commits on the default branch that touch
`.tracker/items/`, and the index records each item's finish commit and date (§6.3). `plan reindex`
therefore needs no network: everything it reads is on disk.

The `dep` table holds the `blocked_by` edges, keyed by item ID on both ends, taken from the ID part
of each entry.

```sql
CREATE TABLE meta       (key TEXT PRIMARY KEY, value TEXT);          -- built_at, schema
CREATE TABLE item       (id TEXT PRIMARY KEY, repo TEXT, path TEXT, title TEXT, type TEXT, status TEXT,
                         estimate INT, priority TEXT, ordinal INT, lane TEXT, milestone TEXT,
                         parent TEXT, started TEXT, finished TEXT, finish_commit TEXT,
                         baseline_start TEXT, baseline_finish TEXT);   -- repo is the prefix
CREATE TABLE label      (id TEXT, label TEXT);
CREATE TABLE dep        (id TEXT, blocked_by_id TEXT);               -- from blocked_by
CREATE VIEW  v_work AS   -- the view every command reads
  SELECT i.*,
         (SELECT count(*) FROM item c WHERE c.parent = i.id)                      AS sub_total,
         (SELECT count(*) FROM item c WHERE c.parent = i.id AND c.status = 'Done') AS sub_completed
  FROM item i;
```

<a id="cli"></a>
## 8. CLI

<a id="reads-and-writes"></a>
### 8.1 Reads and writes

Reads are implicit and writes are deliberate. Whether an operation can make a wrong decision sets
which is which:

- A query reads the files in the working tree and the local git history, so it needs no network
  and no refresh step. The index is rebuilt whenever a file it was built from has changed.
- A write changes files in the working tree and commits nothing. The change is committed on the
  item's branch and reaches the default branch through a pull request, like code. Only `start` and
  `stop` commit, and they commit to the default branch (§8.2).

`new`, `set`, `ice` and `schedule` are immediate, while `freeze` is dry by default. The first group
writes a value the user just typed, so a confirmation prompt would only add a keystroke to a decision
already made. `freeze` writes values the tool derived across many items, where a dry run is the only
chance to catch a wrong inference before it is committed. The dividing line is who chose the value,
whatever the number of rows. `start` and `stop` are immediate too: the user named the item.

Every write regenerates `ready.yml` ([architecture §7.6](../architecture.md#ready-file)).

<a id="commands"></a>
### 8.2 Commands

Query commands are always safe. The Phase column says when each command ships (§3); §2 lists what
Phase 1 leaves out.

| Command | Does | Phase |
|---|---|---|
| `plan status` | Counts, `needs-triage` list | 1 |
| `plan list [--lane frontend] [--milestone beta] [--label kind:bug] [--ready]` | Filtered items | 1 |
| `plan show tunep` | One item: its fields and body, its start and finish, and its PR links | 1 |
| `plan next [--lane L]` | One answer: the single task to start now | 1 |
| `plan ready` | One per lane: the parallel view, for concurrent sessions | 1 |
| `plan why tunep` | Why this item is not startable: blocked by, behind a lane head, iced, or unestimated | 1 |
| `plan board` | Terminal lane board, ASCII columns | 1 |
| `plan validate` | The lint. Non-zero exit. Runs in the pre-commit hook and before `freeze` | 1 |

Commands that write a value the user named take effect immediately, in the working tree.

| Command | Does | Phase |
|---|---|---|
| `plan new "title" [--type T] [--estimate N] [--lane L] [--milestone M] [--parent ID]` | Draws an ID and writes the file | 1 |
| `plan set tunep --estimate 3 --lane frontend --priority P0` | Validates, then writes; all or nothing (§8.4) | 1 |
| `plan ice tunep` / `plan schedule tunep --milestone beta` | Clear or set the milestone | 1 |

Commands that start or stop work commit to the default branch and push.

| Command | Does | Phase |
|---|---|---|
| `plan start tunep` | Commits the start, pushes, and creates the item's branch from it | 1 |
| `plan stop tunep` | Commits the item back to `Todo`, keeping `started` | 1 |

Commands that write what the tool decided are dry by default and need `--apply` to write.

| Command | Does | Phase |
|---|---|---|
| `plan freeze beta [--apply] [--rebaseline]` | Computes and freezes baselines | 1 |

Maintenance commands:

| Command | Does | Phase |
|---|---|---|
| `plan reindex` | Rebuild SQLite from the committed files and local git history, offline. Always safe, because the index is derived | 1 |
| `plan sync` | Push tool commits kept locally while offline, rebuilding any the default branch has moved past | 1 |
| `plan hooks install` | Write the `post-checkout` and `post-merge` hooks into every repo of the plan, and the pre-commit hook | 1 |
| `plan serve [--port 7420]` | The local web UI, bound to localhost | 2 |
| `plan render` | HTML lane board and timeline into `.tracker/out/` (gitignored) | 2 |

Global flags: `--json` (machine output on every query command), `--repo P` (scope to the repo of
the plan whose prefix is `P`).

`plan new` writes the file and commits nothing:

```
plan new "Retry failed webhook deliveries" --estimate 3 --lane api --milestone beta
  1. draw a word that no file in the repo uses and the blocklist lacks     → wa-tunep
  2. write .tracker/items/wa-tunep.md: front matter, then the outline's headings
  3. regenerate ready.yml
```

`plan start` builds a tool commit ([architecture §7.4](../architecture.md#tool-commits)):

```
plan start tunep
  1. read wa-tunep on the default branch's tip; if it is In Progress there, skip to 5
  2. through a temporary index: status: In Progress, started (unless already set), ready.yml
  3. commit "plan: start wa-tunep" on the tip; move the local default branch by compare-and-swap
  4. git push; if it is rejected because the default branch moved, fetch and go back to 1
  5. create feat/wa-tunep-retry-failed-webhook-deliveries from the start commit
```

The branch's `<type>` comes from the item's `type` (§6.1) and the slug from the title. Offline, step 4 is left to `plan sync`, and the branch is still
created. `plan stop` runs steps 1 to 4 with `status: Todo`, leaves `started`, and creates no branch.

The `post-checkout` hook runs when a branch is checked out. On a branch whose name carries an ID,
it runs steps 1 to 4, then fast-forwards the branch onto the start commit if the branch has no
commits of its own yet, and otherwise writes the same change into its working tree. It always exits
0, because git takes its exit status as the checkout's.

<a id="next-ready-why"></a>
### 8.3 next, ready, why

`plan next` selects in this order, which is the whole algorithm:

1. drop anything `Done`, `Icebox`, or `needs-triage`
2. drop anything blocked by an item that is not `Done`
3. drop anything that is not its lane's head
4. sort by `priority`, then `ordinal`, then ID
5. print the first

A blocker the plan cannot read, such as one in a repo outside the plan, counts as not `Done`.

```python
def candidates(items, done_ids):  # plan.py; blocked_by_ids from the index dep table
    return [i for i in items
            if i.status not in ("Done", "Icebox")
            and i.estimate is not None                    # needs-triage excluded
            and all(b in done_ids for b in i.blocked_by_ids)]

def lane_head(lane_items):
    return sorted(lane_items, key=sort_key)[0]

def sort_key(i):
    return (PRIORITY_ORDER[i.priority], i.ordinal is None, i.ordinal or 0, i.id)
```

- **`next`**: `candidates` ∩ lane heads, sorted, take the first. One line, plus duration and what
  it unblocks.
- **`ready`**: one row per lane, showing the head, its estimate and its unmet blockers. This is the
  concurrency answer, and `ready.yml` holds the same rows.
- **`why ID`**: the negation. Report every reason in order: not estimated · iced · done · blocked
  by an item not `Done` (naming each) · not the lane head (naming the head). It explains a negative,
  which a chart conveys badly anyway.

```
$ plan next
wa-tunep [3] Retry failed webhook deliveries          lane api        P1
    ready · 5d at 5 pts/week · unblocks wa-mefut

$ plan next --lane frontend
wa-ridal [5] Settings page: notification preferences  lane frontend   P2
    ready · 7d · head of lane (3 behind it)

$ plan ready
LANE       TAKE      EST  BLOCKED BY
api        wa-tunep  3    —
frontend   wa-ridal  5    —
docs       wa-lavon  1    —
infra      ba-kipes  2    wa-tunep wa-lavon

$ plan why mefut
wa-mefut not startable
  · blocked by wa-tunep (Todo), wa-lavon (In Progress)
  · behind lane head wa-ridal in lane frontend
```

All three take `--json`, so an agent can consume them without parsing columns.

`duration_days = max(1, ceil(estimate / points_per_week * 7))`. Elapsed calendar time, with no
weekend exclusion: the idle days are already inside the rate.

<a id="set"></a>
### 8.4 set

`plan set ID` edits the fields of one item. It is the command-line alternative to editing
`.tracker/items/<id>.md` by hand, and it runs the same checks. It writes the file in the working
tree; committing it is the user's.

| Flag | Writes | Clear with |
|---|---|---|
| `--title T` | `title` | cannot be cleared |
| `--type {feat,bug,chore}` | `type` | cannot be cleared |
| `--estimate {1,2,3,5}` | `estimate` | `--estimate none` (the item becomes `needs-triage`) |
| `--priority P0..P3` | `priority` | cannot be cleared; the default is `P2` |
| `--status S` | `status`: `Todo`, `Blocked` or `Done` (§6.3) | cannot be cleared |
| `--ordinal N` | `ordinal` | `--ordinal none` |
| `--lane L` | `lane`, which must be in `config.lanes` | `--lane none` (the item becomes `needs-triage`) |
| `--label L` | adds `L` to `labels` | `--unlabel L` |
| `--parent ID` | `parent` | `--parent none` |
| `--blocked-by ID` | adds `"<id> - <title>"` to `blocked_by` | `--unblock ID` |

Other fields have their own commands: the milestone through `ice` and `schedule`, `started` through
`start`, the baseline through `freeze`. `set` rewrites the title part of every `blocked_by` entry
from the item it names.

**All or nothing.** `set` applies every flag to a copy of the item, then runs every `ERROR` rule in
§9 that concerns this item against that copy, including the rules that look at other items to judge
it: a parent with children carrying an estimate, and a cycle across the plan.
Findings about other items do not block it. If any rule fails, the command writes
nothing, prints every failing rule rather than only the first, and exits 1. If all pass, it writes
the file once. `WARN` findings are printed but do not block the write.

Some consequences of running the full rule set:

- `--status In Progress` fails, naming `plan start`, which records `started`. `--status Icebox`
  fails, naming `plan ice`, which clears the milestone.
- `--status Done` also writes the `actual_time` snapshot when a time source is configured. A source
  that fails does not block it ([design 0002, *When the snapshot is taken*](0002-tracked-time.md#lifecycle)).
- `--estimate 8` and `--estimate 13` always fail, with the message telling you to split the item.
- `--blocked-by` that would close a cycle fails, naming the cycle.
- `--title` leaves other items' `blocked_by` entries naming the old title until each one is next
  written. `validate` warns about them in the meantime.

`set` writes immediately, with no dry run, because the user typed every value (§8.1).

<a id="validation"></a>
## 9. Validation rules

`validate.py` has one function per rule, each returning zero or more findings. Exit 1 if any
`ERROR`.

The cycle rule runs over the `blocked_by` graph of the whole plan, so a cycle that crosses repos is
found. An item blocked by itself is a cycle of one. A reference is unresolved when its prefix
belongs to no repo the plan reads, as when a repo is validated on its own. That is a warning, and
the check waits for a plan that lists both repos. A reference whose prefix the plan reads but whose
item does not exist is an error.

| Rule | Level | Message |
|---|---|---|
| estimate in {1,2,3,5} | ERROR | `wa-tunep estimate 8 is a refusal code, not a size — split it` |
| parent with children has no estimate | ERROR | `wa-ridal has 3 children and an estimate; roll-up would double-count` |
| `lane` in the repo's `config.lanes` | ERROR | `wa-tunep lane 'x' is not configured` |
| no cycle in the plan's `blocked_by` graph | ERROR | `cycle: wa-tunep -> ba-kipes -> wa-lavon -> wa-tunep` |
| `blocked_by` and `parent` name an item that exists | ERROR | `wa-tunep is blocked by wa-zobet, which has no file` |
| `blocked_by` and `parent` resolve in this plan | WARN | `wa-tunep is blocked by ba-kipes; no repo in this plan has prefix 'ba'` |
| `blocked_by` title matches the item it names | WARN | `wa-mefut names wa-tunep 'Retry webhooks'; its title is 'Retry failed webhook deliveries'` |
| blocked-by is intra-milestone | WARN | `wa-tunep is blocked by wa-lavon in a different milestone; milestone order already implies it` |
| milestone absent ⟺ status Icebox | ERROR | `wa-tunep has no milestone but is not Icebox` |
| item file matches the schema | ERROR | `wa-tunep: status 'In Review' is not one of Icebox, Todo, In Progress, Blocked, Done` |
| file name is an ID with the repo's prefix | ERROR | `.tracker/items/tunep.md is not named <prefix>-<word>.md with prefix 'wa'` |
| each ID names one file in the plan | ERROR | `wa-tunep is defined in web-app and in ../billing-api` |
| member repos' prefixes are unique | ERROR | `web-app and ../billing-api share prefix 'wa'` |
| member repo exists on disk | WARN | `member ../billing-api is missing; the plan is answered without it` |
| item `milestone` names a milestone file | ERROR | `wa-tunep milestone 'gamma' has no .tracker/milestones/gamma.md` |
| repo milestone does not shadow a plan milestone | WARN | `ba-kipes: milestone 'beta' in ../billing-api hides the plan's 'beta'` |
| milestone `order` unique | ERROR | `beta and gamma share order 200` |
| stored Blocked agrees with blocked-by | WARN | `wa-tunep is Blocked but no unfinished item blocks it` |
| `ordinal` unique within a lane | WARN | `wa-tunep and wa-ridal share ordinal 200 in lane api` |
| an item's branch contains its start | WARN | `feat/wa-tunep-retry does not contain plan: start wa-tunep` |
| an item's branch prefix matches its `type` | WARN | `fix/wa-tunep-retry is a bug branch; wa-tunep is a feat` |
| estimate and lane present | WARN | `wa-tunep needs triage` |

The branch rules check the local branches whose names carry an ID. The rules on tracked time,
including a `started` later than the first tracked time, are in
[design 0002, *Index and validation*](0002-tracked-time.md#index).

<a id="github-interaction"></a>
## 10. GitHub and git interaction

Every call lives in `gh.py` / `git.py`. Nothing writes through GitHub's API; the only remote write is
`git push` of the tool's own commits. The complete Phase 1 set:

| Purpose | Call |
|---|---|
| Default branch | `git symbolic-ref refs/remotes/origin/HEAD` |
| Actual finish | `git log --first-parent <default> -- .tracker/items/`, then each commit's copy of the item files (§7) |
| Build a tool commit | `git read-tree`, `git update-index` and `git write-tree` with `GIT_INDEX_FILE` set to a temporary file, then `git commit-tree` on the default branch's tip |
| Move the local default branch | `git update-ref refs/heads/<default> <new> <old>`, which fails if the branch moved |
| Share a tool commit | `git push origin <default>`; on a rejection, `git fetch origin <default>` |
| Create the item's branch | `git switch -c <type>/<id>-<slug> <start>` |
| Branches in flight, for `ready.yml` | `git for-each-ref refs/remotes/origin/`, as of the last fetch |
| Branch contains its start | `git merge-base --is-ancestor <start> <branch>` |
| Pull request links | `gh pr list --state all --json number,url,headRefName`, read-only; matched to items by the ID in the branch name |
| Rate limits | none apply: the tool makes no GitHub mutations, and `gh pr list` runs once per repo for a report that shows PR links |

<a id="testing"></a>
## 11. Testing

- `validate.py` and `plan.py` are pure: fixtures in, findings out. Cycle detection and
  `next` selection get a case each per branch, because these are the two places a bug is silent.
  The cycle cases include a three-item cycle and one that crosses repos.
- `gh.py` is mocked by recorded output; no network in the suite. `git.py` and `start.py` run against
  temporary git repos the tests create, with a bare repo as `origin`: the start commit, the
  compare-and-swap, a rejected push and its rebuild, and the finish read from history.
- The fixtures live in `tests/fixtures/` ([README](../../tests/fixtures/README.md)). `valid/web-app/` is a two-repo plan, `web-app` listing `billing-api` as a member, that passes every rule. `broken/<rule>/` holds one tree per §9 rule, named for it. Each tree is a tracker root. Recorded `gh pr list` output is in the shape of the gh version the README names.
- One end-to-end test over `valid/web-app/` asserts that `validate` exits 0 and `next` returns
  the `billing-api` item the README names.
